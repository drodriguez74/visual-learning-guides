01 The Triage Protocol

Same order every time, whether the patient is a single ReAct loop or a twelve-node supervisor graph. Skipping straight to "diagnose" on a live incident is how a recursion loop burns your token budget while you're still reading logs.

01 — INTAKE

Confirm it's real

Pull the run/thread ID. Is it one bad trace or a fleet-wide pattern? Check error rate, not anecdote.

02 — ASSESS

Tag severity

Is money/data/safety at risk right now (CRITICAL), quality degrading (DEGRADED), or a single odd trace (WARNING)?

03 — STABILIZE

Stop the bleed

Kill switch, pause the thread, or cap recursion/tokens before you touch root cause. Stop damage first.

04 — DIAGNOSE

Read the trace

LangSmith waterfall, get_state_history(), checkpoint diffs. Find the node where reality diverged from intent.

05 — TREAT

Fix + verify

Patch the node, reducer, or prompt. Replay against the exact failing input before calling it closed.

06 — DEBRIEF

Prevent recurrence

Add the case to the eval set. A failure mode you can't re-trigger in CI will happen again.

02 Symptom Board

Fifteen failure modes seen in LangChain/LangGraph agents running in production, indexed by how they present. Filter by severity to work the board like an actual queue.

CASE 01CRITICAL

Recursion loop / non-termination

SYMPTOMGraph keeps re-entering the same nodes; run finally dies on GraphRecursionError, or worse, never dies.
LIKELY CAUSEConditional edge with no real exit condition; the LLM keeps deciding "I need more info" and re-calling the same tool.
DIAGNOSEfor s in graph.get_state_history(config): print(s.next, len(s.values["messages"])) # look for repeating node sequence
STABILIZELower recursion_limit to fail fast; kill the thread.
FIXAdd an explicit loop counter to state; route to END past N iterations regardless of LLM's opinion.
CASE 02WARNING

Tool call failure / malformed args

SYMPTOMToolException, invalid JSON args, or a 4xx bounced back from a downstream API.
LIKELY CAUSETool schema drifted from what the model was trained/prompted on, or the API contract changed underneath you.
DIAGNOSEIn the trace, compare the emitted tool_call.args against the tool's actual Pydantic schema — the mismatch is usually one field.
FIXCatch, return the error as a string back into state so the model self-corrects, instead of raising.
PREVENTStrict schemas via with_structured_output; contract tests on the underlying API.
CASE 03CRITICAL

State corruption / bad reducer

SYMPTOMA state field gets silently overwritten, or a list field duplicates/loses entries after parallel branches merge.
LIKELY CAUSEMissing or wrong Annotated reducer — default channel behavior overwrites instead of merging.
DIAGNOSEhistory = list(graph.get_state_history(config)) # diff .values between consecutive checkpoints # to see exactly which node wrote which key
FIXDefine the reducer explicitly, e.g. Annotated[list, add_messages], and own each key by exactly one node.
CASE 04DEGRADED

Context window overflow

SYMPTOM"Maximum context length" errors, or worse — silent truncation and steadily degrading answer quality mid-run.
LIKELY CAUSEUnbounded message history in a long-lived loop; raw tool output dumped into state instead of summarized.
DIAGNOSELog token count per node call; inspect message list length in the state snapshot at the failing step.
FIXUse trim_messages or a summarization node; cap tool-output size before it's appended.
CASE 05CRITICAL

Provider outage / rate limit

SYMPTOM429s and 5xxs from the model API, timeouts cascading across many concurrent runs at once.
LIKELY CAUSENo backoff strategy; single-provider dependency; a traffic burst above your negotiated rate limit.
DIAGNOSECorrelate error timestamps across traces — a shared spike means it's the provider, not your graph.
STABILIZEExponential backoff + jitter; circuit breaker; fail over to a secondary model.
CASE 06CRITICAL

Token / cost runaway

SYMPTOMA spend alert fires, or one run's token count is orders of magnitude above the norm.
LIKELY CAUSEA loop combined with large context re-sent on every turn — often riding alongside Case 01 or 04.
DIAGNOSESort LangSmith runs by token count, isolate the outlier trace, walk its node sequence.
STABILIZEA budget-guard node that halts the run once it crosses a per-thread token threshold.
CASE 07DEGRADED

Latency degradation

SYMPTOMp95 run time creeping up over days/weeks; downstream services start timing out waiting on the agent.
LIKELY CAUSESequential LLM calls that could run in parallel; a slow tool/API call; cold-started infra.
DIAGNOSERead the trace waterfall — find the single longest span, not the average.
FIXFan-out independent nodes and fan-in the results; cache repeat retrieval calls.
CASE 08WARNING

Hallucinated tool selection

SYMPTOMAgent invokes a tool that doesn't exist, or calls the right tool for the wrong purpose.
LIKELY CAUSEToo many tools exposed at once, ambiguous tool descriptions, or a weak routing prompt.
DIAGNOSECompare the emitted tool_call.name against the tool list actually bound at that node.
FIXNarrow the tool surface per step (role-scoped toolsets); sharpen descriptions with concrete examples.
CASE 09CRITICAL

Checkpointer / persistence failure

SYMPTOMResume fails with "no state found for thread_id," or a checkpoint comes back corrupted.
LIKELY CAUSECheckpointer backend (Postgres/Redis) connectivity issue, or a custom object in state that isn't serializable.
DIAGNOSEconfig = {"configurable": {"thread_id": tid}} state = graph.get_state(config) print(state) # None or error → backend issue
STABILIZEFail over to a backup checkpointer; ensure every state field is plain-serializable.
CASE 10DEGRADED

Stuck human-in-the-loop interrupt

SYMPTOMA thread has been sitting at interrupt() for hours; nobody resumed it.
LIKELY CAUSENo timeout on pending approvals, or the UI never actually surfaced the interrupt payload to a human.
DIAGNOSEQuery threads by status for anything parked past its expected review SLA.
FIXResume with a safe default via Command(resume=...), or auto-escalate past a timer.
CASE 11WARNING

Silent wrong output

SYMPTOMNo exception at all — the run completes cleanly, but the answer is wrong or off-policy. The scariest failure mode.
LIKELY CAUSEEval coverage gap, missing guardrail node, or silent drift after a prompt or model version bump.
DIAGNOSEDiff the run against your golden eval set; walk the reasoning trace, not just the final answer.
FIXAdd an output-validation node; roll back the prompt/model change that shipped closest to the regression.
CASE 12CRITICAL

Multi-agent handoff failure

SYMPTOMOrchestrator and sub-agent deadlock; a message never routes back, or the same work runs twice.
LIKELY CAUSEMismatched handoff schema between agents, a missing routing edge, or two agents writing the same state key.
DIAGNOSETrace every inter-agent Command(goto=...) call; map which agent owns which state key.
FIXDefine an explicit handoff contract; namespace state keys per agent so writes can't collide.
CASE 13CRITICAL

Prompt injection / unsafe output

SYMPTOMAgent follows instructions embedded in a retrieved doc or tool output — leaks data, takes an unauthorized action.
LIKELY CAUSEUntrusted content (web page, email, doc) flowed straight into the planning context, unsanitized.
DIAGNOSETrace which node first ingested the untrusted content, and what tool calls followed it.
STABILIZEKill the run. Sandbox tool execution; require human approval on any sensitive tool.
CASE 14WARNING

Non-deterministic / flaky output

SYMPTOMIdentical input, different output across runs; eval suite passes and fails on the same case unpredictably.
LIKELY CAUSETemperature above 0 with no seed, or a parallel fan-in whose merge order isn't fixed.
DIAGNOSERerun at temperature=0 with a fixed seed; compare traces side by side.
FIXPin seed for debugging sessions; make the fan-in merge logic order-independent.
CASE 15CRITICAL

Cache staleness / cross-thread leakage

SYMPTOMAgent returns an answer that was true last week but not now, or — far worse — one user's cached response surfaces in another user's thread.
LIKELY CAUSESemantic/response cache keyed on a similarity threshold instead of exact context; cache key missing thread_id/tenant scope; TTL longer than the underlying data's real shelf life.
DIAGNOSEReproduce with cache disabled and diff the output; check the cache key actually built for the failing call — look for what scope it's missing.
STABILIZEFlush the cache or disable it for the affected route/tenant immediately if there's any cross-user exposure — this is a data-leak incident, not a quality bug.
FIXScope cache keys to tenant + thread + a hash of the exact input; set TTL to match true data volatility, not convenience.
PREVENTCache-key unit tests asserting isolation across tenants/threads; alert on cache hit-rate anomalies as a security signal, not just a performance one.
03 Diagnostic Toolkit

The instruments you actually reach for once a case is stabilized and you're working root cause.

Turn on tracing before you need it

Every run should already be shipping to LangSmith. If it isn't, this is step zero of every future incident.

# .env
LANGCHAIN_TRACING_V2="true"
LANGCHAIN_API_KEY="..."
LANGCHAIN_PROJECT="agent-prod"

Walk state history, not just the final state

The bug is almost always in a transition, not a snapshot.

for step in graph.get_state_history(config):
    print(step.next, step.metadata["step"])
    # inspect step.values at the point it diverges

Stream in debug mode for a live incident

Full event stream, not just final output — see every node enter/exit as it happens.

for event in graph.stream(
    inputs, config, stream_mode="debug"
):
    print(event)

Cap the blast radius by default

Recursion and token limits are cheap insurance against Cases 01 and 06.

graph.invoke(
    inputs,
    config={
        "recursion_limit": 25,
        "configurable": {"thread_id": tid},
    },
)
04 Escalation Matrix

Severity determines urgency, not effort. A CRITICAL case can have a one-line fix; the escalation speed is about the blast radius while it's open.

SeverityDefinitionResponseOwner
CRITICAL Money, data, or safety actively at risk — runaway cost, corrupted state, unsafe tool execution. Page on-call now. Stabilize (kill switch / cap) before diagnosing. On-call engineer
DEGRADED System still functioning but quality, latency, or throughput is measurably worse than baseline. Monitor the trend; fix within the current sprint. Owning team
WARNING Single odd trace or edge case with no fleet-wide signal yet. Log it, add to the eval backlog, watch for recurrence. Backlog
05 The 5-Second Walkthrough

A flat ~5s tax on every call is specific enough to have a short list of usual suspects. Work this list top to bottom before you go spelunking — check them in order, stop at the first one that accounts for most of the time.

01

Read the waterfall, not the total

Pull the trace and look at individual span durations. If one node eats 4+ of the 5 seconds, that's the whole investigation — everything else is noise.

for event in graph.stream(
    inputs, config, stream_mode="debug"
):
    print(event["type"], event.get("timestamp"))
# diff consecutive timestamps → find the gap
02

Sequential LLM calls that could be parallel

Plan → select-tool → call-tool → synthesize run in series adds up fast even at ~1s a hop. If the nodes don't depend on each other's output, they shouldn't be chained.

# serial — 4 hops, 4x latency
plan → select_tool → call_tool → synth

# parallel — fan out independent branches
graph.add_edge("plan", ["tool_a", "tool_b"])
# fan-in on a shared reducer
03

Cold start

First call after idle time — serverless endpoint spin-up, lazy-loaded vector store, a fresh connection pool — is often the entire 5s by itself. Check whether it's every call or only the first in a burst.

# quick test: fire two calls back to back,
# compare call #1 vs call #2 latency
t0 = time.time(); graph.invoke(inputs, config)
t1 = time.time(); graph.invoke(inputs, config)
print(t1 - t0)  # call 1 (cold)
04

Retrieval or re-embedding on every turn

A vector store query or a document re-embed that runs on each node visit is a common silent 1-3s tax, especially once it's no longer being cached from an earlier design pass.

# check: is this node re-embedding
# the same content it embedded last turn?
retriever.invoke(query)  # time this in isolation
05

Hidden retry / backoff

If exponential backoff was added for rate limits (Case 05), a single silent retry can be 2-4s on its own — and it won't show up as an error, just as slowness.

# check retry logs/counters for this run —
# a "successful" call may have retried once
logger.info(f"attempt={attempt} elapsed={elapsed}")
