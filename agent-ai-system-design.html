00 — Recap

What Makes a System "Agentic"

A basic LLM application takes an input, sends it to a model, and returns an output. An agentic AI system goes further: it can decompose a goal, decide which step to take next, call external tools, inspect the tool result, update its state, and continue the workflow until it reaches a stopping condition.

An agentic AI system isn't just an LLM wrapped inside a chat interface — it's a production software system where a model reasons over a goal, uses tools, retrieves context, maintains state, and makes decisions across multiple steps that trigger real actions through APIs.

The Agentic Loop
"The hard part isn't just getting a model to answer. The hard part is designing a system that is reliable, cost-aware, fast enough for the user experience, context-aware, observable, and safe enough to connect to real tools."
01 — Topology

Single-Agent vs Multi-Agent Systems

At a high level there are two common patterns for organizing an agentic system.

Two Control-Loop Topologies
Example from the video — single agent A customer support agent may classify a request, retrieve an account context, call a billing API, ask for confirmation, and then generate a final response — one primary agent owns the whole workflow, even while calling multiple tools.
Example from the video — multi-agent One agent may handle planning, another retrieve knowledge, another write code, another review the output, and another handle execution. Multi-agent systems are useful when the task has clear specialization, parallel work, review loops, or long-running workflows.
When multi-agent pays off
  • Clear specialization between roles
  • Genuinely parallel work
  • Review loops before final output
  • Long-running workflows
What multi-agent costs you
  • More coordination overhead
  • More failure modes
  • More state to track, more logs to inspect
  • More places where cost and latency increase
02 — Architecture

The Six Building Blocks

Once you understand the context, the next step is the building blocks: the model layer, tools, memory & state, orchestration, evaluation, and approval & policy control.

How the Blocks Connect
1Model Layer
Model Layer & Routing
The actual LLM (or multiple models) plus the strategy for when each one gets used.
Route by Complexity
Why routing matters
  • A single powerful model handling every step gets expensive and slow very quickly.
  • Use cheaper, faster models for low-complexity steps: intent classification, routing, extraction, schema filling, simple summarization.
  • Reserve stronger reasoning models for steps where deeper reasoning actually changes the outcome — e.g. ambiguous constraints like "I'm traveling next week, avoid mornings."
  • Use structured outputs at the model layer: JSON schema, Pydantic models, function/tool calling — any step feeding another system should return predictable structure, not free-form prose.
The model layer must answer three questions
  • What model is used for this specific step?
  • What output contract does it return?
  • What happens if the model fails and returns invalid output?
Example from the video In an appointment-booking agent, you don't need a frontier model to detect book / reschedule / cancel / ask-a-question — a small model classifies that fine, and you may not need an LLM at all to extract date, time, doctor name into a JSON schema.
2Tools
Tools
The interface between the model and the external world — designed like APIs, not conversations.
Bad vs Safer Tool Contract
What a tool can be
  • Database lookup, CRM API, calendar API, payment API, code interpreter, internal search service, ticketing system, Slack action, Google action — any back-end function the agent is allowed to call.
Every tool needs
  • Clear name and description
  • Input schema and output schema
  • Permission boundaries and timeout / retry behavior
  • A structured error format — failures return structured errors, successes return structured results. The agent should never have to parse messy prose from your back end.
Design pattern: separate read from write
  • Start with read-only capabilities.
  • Add low-risk write tools.
  • Add high-risk write tools only with validation and human approval — fetching available appointment slots is very different from cancelling an appointment.
On MCP Model Context Protocol (MCP) is an emerging pattern for exposing tools, resources, and context to agents in a standardized manner. But even without MCP, the design principle is the same: tools need contracts, permissions, boundaries, and logs.
3Memory & State
Memory & State
Where many agentic systems become messy. Memory is not one thing — and it isn't the same as state.
State vs Memory
Choose storage by access pattern — not "everything into a vector DB"
Data typeStoreWhy
Conversation & workflow stateRedis · DynamoDB · Postgres · MongoDBLow latency
Application stateApp databaseBelongs with the rest of your app
Knowledge retrieval (RAG)Pinecone · pgvector · Weaviate · Elasticsearch · OpenSearchSemantic search
Long-term archiveS3 / object storageCheap, cold storage
Short-term context vs long-term memory
  • Short-term context is what you pass into the process for the current turn.
  • Long-term memory is retrieved selectively — the goal is not to stuff everything into the context window (that creates context bloat). Retrieve the smallest useful context for the current decision.
  • Memory design is really data architecture: what to store, where, how long to keep it, how to retrieve it, and whether it's safe to send to the model.
Example from the video Rescheduling a doctor's appointment: appointment ID, proposed new time, confirmation status, workflow step → structured workflow state. The user's medical history should not be casually passed through the LLM if the model only needs the appointment ID and available slots.
4Orchestration
Orchestration
The control layer that coordinates the model, tools, and memory — and defines how the system moves from request to final output.
Explicit Control Flow
Implementation options
  • Plain application code
  • Graph-based framework (e.g. LangGraph)
  • Workflow engines (Temporal, LlamaIndex workflows, LangChain), custom state machines — or a combination
Pipeline vs agentic reasoning
  • For simple use cases, a deterministic pipeline is often better than a fully autonomous agent loop — not every workflow needs planning and reflection.
  • If the sequence of steps is mostly known, design it as a pipeline or state machine. Use agentic reasoning only when the workflow genuinely needs dynamic decision-making.
  • For complex systems, graph-based orchestration represents branching, retries, loops, approval gates, and fallback paths (e.g. no available appointment → suggest an alternate; cancellation request → confirmation path).
  • Multi-agent orchestration also needs agent-to-agent routing: which agent takes the next step, what information passes between them, expected output format, and how conflicts are resolved.
"Do not confuse autonomy with lack of structure. Production agents need a very clear control flow."
5Evaluation
Evaluation
One of the most important yet ignored parts of agentic AI system design. "No exception thrown" does not mean the system worked.
Trace-Level Evaluation
What can silently go wrong
  • Return valid JSON that is semantically wrong
  • Call the correct tool with the wrong arguments
  • Retrieve irrelevant or stale context
  • Fail to ask for confirmation, refuse a valid request, or comply with an unsafe one
Build the eval system
  • Maintain a test set of realistic scenarios: happy path, ambiguous requests, out-of-scope requests, tool failures, malicious inputs, partial information, policy edge cases, escalation cases.
  • Re-run it as a regression test whenever the model, prompt, retrieval logic, or tool schema changes.
  • Run sampled async evaluations in production; an LLM-as-judge can score a percentage of conversations offline, plus high-signal user feedback.
  • LLM-as-judge is useful but not perfect — for important flows, combine model-based grading with deterministic checks and human review.
Metrics to track Intent accuracy · tool call success rate · invalid schema rate · retrieval hit rate · refusal accuracy · escalation rate · task completion rate · user flag rate · cost per successful task.
6Approval & Policy
Approval & Policy Control
Not every action needs human approval — but high-impact actions should always have gates.
The Approval Gate Pattern
Actions that always need a human in the loop
  • Sending an email · deleting data · issuing a refund
  • Cancelling an appointment · changing billing · updating a CRM record
  • Running code · placing an order · making a financial transaction
Validation should be deterministic wherever possible
  • Check ownership, check permissions
  • Check whether the requested action is allowed under policy
  • Check required fields are present
  • Check the user has confirmed the exact action — then execute
Multi-agent note If one agent generates a plan and another executes it, the execution layer must not blindly trust the planning layer. Tool execution still needs validation and authorization. The agent should not be the source of truth for your business rules — your application code should be.
03 — Production Engineering

The Four Production Principles

Now that you have the main building blocks, these are the principles that hold the entire system together.

1Reliability
Reliability
The system behaves predictably even when the model does not.
Reliability Layers
How you get reliability
  • Decompose large prompts into smaller steps — one joint prompt that classifies intent, retrieves context, decides policy, calls tools, and writes the final response is very hard to test. Smaller steps are easier to evaluate and debug.
  • Use structured outputs. If the next step depends on the model's output, validate the schema; if invalid, retry; if it still fails, use a fallback path.
  • Wrap every model call like an unreliable upstream dependency: handle timeouts, malformed outputs, rate limits, provider errors, degraded quality.
  • Separate deterministic validation from model reasoning — if the model extracts a date, code validates the date; if it selects a user ID, code verifies permissions; if it proposes a tool call, code validates the arguments.
2Cost & Latency
Cost & Latency
Agentic systems often involve multiple model calls per request — cost and latency must be designed together.
One Request, Many Calls
Levers
  • Model routing — small models for classification/extraction, larger models only when ambiguity, reasoning, or synthesis is required.
  • Limit tokens aggressively — output tokens are both a cost and a latency lever. A two-sentence answer doesn't need a long explanation; a downstream JSON consumer doesn't need prose.
  • Caching for retrieval results, repeated policy lookups, tool metadata, and stable context.
  • Batching & async execution for non-blocking work like evaluation and summaries.
  • Streaming responses for user-facing tasks; show progress for long-running tool calls instead of a blank screen.
  • Enforce scope early with cheap filters/rules/intent gates — out-of-scope requests shouldn't burn tokens on expensive reasoning.
  • Cost observability: tokens in/out, cost per step, per conversation, and per successful task.
3Context & RAG
Context & RAG Design
The biggest difference between a toy agent and a useful production agent. The goal is not to pass everything into the prompt.
Context Sources → Current Step
RAG retrieval quality > just having a vector database
  • Document chunking · metadata filters · hybrid search when useful
  • Reranking · freshness controls · source attribution when trust matters
Separate trusted instructions from untrusted content
  • Retrieved documents should never override the system instructions.
  • Tool outputs are data, not instructions.
  • End-user content should be isolated from developer/system instructions.
  • For long conversations, use summarization and checkpoints instead of passing full history forever — store the summary separately from raw logs and track what it's allowed to influence.
"A context-aware system is one that knows what information it needs, where it should be retrieved from, whether it is trusted or not, and whether it is safe to send to the model."
4Observability, Security & Privacy
Observability, Security & Privacy
The final production layer. Treat everything that touches the model as attacker-controlled input, unless proven otherwise.
Untrusted Inputs → Isolation → Execution
Observability — log the anatomy of every agent run
  • Model name/version, prompt version, step name, workflow ID, conversation ID
  • Tool name, tool arguments (mask sensitive values)
  • Latency, time-to-first-token, tokens in/out, cost
  • Retries, fallbacks, errors, feedback used, eval scores
  • Should answer: where did the failure happen — intent classification, retrieval, planning, tool selection, tool execution, policy validation, or final response?
Security
  • Isolate untrusted content — separate instructions from data.
  • Never execute raw model output — no SQL or shell commands run directly from model-generated text.
  • Give tools least-privilege permissions; add approval gates for risky actions.
Privacy
  • Send the minimum data needed — an appointment ID and availability, not the full patient report; a summarized ticket, not full customer history.
  • Mask PII at the right time; set retention policies for logs, traces, and conversation archives.
  • Your model provider, vector database, observability platform, and logging systems are all part of your data boundary.
"This is why agentic AI system design is not just about prompt engineering. It is backend design, data design, security design, and product design — with an LLM in the loop."
